## 当前结论与确认内容

### 目标与总体结构

- 岗位创建请求完成输入校验和持久化后快速返回，不再在请求线程和数据库事务中等待 CPA。
- 正常目标为 10 分钟内开始解析；预计超过 30 分钟继续接收并提示等待较长；预计超过 2 小时拒绝新建和手动重新解析，不创建任务，也不消耗成功提交次数。
- MySQL 保存岗位、持久化解析任务、任务代次、候选画像和用户排队号，是任务恢复和结果写入的最终事实来源。
- Redis 是岗位写操作和调度的必备依赖，负责同一用户的分布式锁、等待用户队列、文件上传次数和快速调度；不新增用户控制表，但持久化解析任务结构仍然必须存在。
- MySQL 唯一约束防止任务和排队记录重复；Redis 锁只覆盖同一用户的短时检查与数据库写入，不覆盖文件提取或 CPA 调用。
- MySQL 已提交而 Redis 尚未更新的任务必须能够根据持久化记录补回，避免数据库与 Redis 双写窗口丢任务。

### 公平排队与容量

- 每个用户每轮只解析一个岗位；该用户还有等待任务时，完成本轮后使用新的固定排队号重新进入队尾。
- 新用户只能加入当前队尾，不能插到已经等待的用户前面；同一用户的多个岗位按提交顺序依次等待。
- Redis 丢失队列数据或服务重启后，按 MySQL 中持久化的排队号恢复顺序，不能重新按任意扫描顺序洗牌。
- 后台全系统并发数限制的是“同时调用多少个 CPA 请求”，不是“最多接收多少个任务”；未获执行额度的任务继续排队，不直接失败。
- 实时面试必须使用独立 CPA 容量；岗位、简历等后台任务只能使用后台容量。CPA 账户、Key、路由和实际并发数由其他负责人提供，后端以配置接入，不写死为 2。
- 只有真正获得后台执行额度的任务才创建虚拟线程；等待任务只保存在 MySQL 和 Redis 中，不占用线程或 HTTP 连接。

### 数量、频率与输入保护

- 每个用户最多保留 5 个未归档岗位；等待、失败、待确认和已确认等未归档岗位都计入。归档立即释放位置，恢复时必须有空余位置。
- 每个用户最多有 5 个等待解析任务。
- 新建和手动重新解析每个用户每 5 分钟最多成功提交一次；缓存命中也算成功提交。文件校验失败或全局预计等待超过 2 小时不消耗该次数。
- 每个用户每 5 分钟最多向服务端提交 5 次文件上传请求，成功和失败都计入该上传保护；页面本地选择或删除文件不计算。
- 岗位文件最大 10MB，只接受真实内容为 PDF 或 TXT 的文件，不能只相信扩展名或客户端 fileType。
- 粘贴或提取后的岗位 JD 最多 2000 个字符，超限明确拒绝，不静默截断；该限制只适用于岗位，不在本次方案中改变简历限制。
- 粘贴文本在前端显示字数并阻止超限提交，后端再次校验；文件类型和大小由前后端校验，PDF/TXT 提取后的字数由后端最终判断并由前端展示错误。
- PDF 文本提取设置可配置的并发上限，防止大量文件同时占用 CPU 和内存。

### CPA 调用、超时与结果

- 岗位解析保留非流式完整响应，页面不展示逐字内容；后台虚拟线程等待完整 JSON。
- 单个岗位解析的绝对总时限为 15 分钟，主模型、备用模型和内部处理共享该时间，备用模型不能重新获得一份 15 分钟。
- 超时必须配置到实际 HTTP 客户端并确保取消会关闭底层连接；只在虚拟线程外层计时或中断线程不算完成超时治理。
- 保留明确的模型输出上限；当前 4096 token 是输出安全上限，不是 JD 输入长度限制。
- ChatClient 和底层连接池必须按稳定的 CPA 路由与模型配置复用，不能每次调用重新创建。
- CPA 明确返回短暂繁忙或连接尚未建立就失败时，只自动重新排队一次，并回到公平队列；其余失败由用户手动重试。
- 超时、空响应、无效 JSON 和模型故障必须进入失败状态，不能再返回兜底画像并被当作成功。
- 日志不得记录 JD 原文、完整模型响应、CPA Key 或其他敏感内容，只记录任务 ID、状态、耗时、响应长度和脱敏错误类型。

### 画像版本、缓存与重试

- 第一次解析没有旧画像时，岗位按等待、解析、待确认或失败展示。
- 已确认岗位重新解析时，旧正式画像继续可用于新建面试；新结果独立保存为候选版本，用户确认后才替换正式画像。
- 新候选结果失败或取消不影响旧正式画像；确认新版本后重新进入待审核，并在审核通过前退出公共岗位列表。
- 每次新建、重新解析、取消或恢复相关任务都通过任务代次和期望状态保护；旧任务晚到结果不得覆盖新的任务、归档状态或正式画像。
- 新建岗位可使用“规范化 JD 摘要 + 提示词版本 + 输出结构版本 + 模型标识”的精确成功缓存并绕过 CPA 队列。
- 缓存使用安全摘要；失败、空结果、损坏 JSON 和用户编辑确认后的正式画像不进入模型候选缓存。
- 用户主动点击重新解析时必须绕过缓存并真正调用 CPA。
- 页面失败状态直接提供重新解析按钮；手动重试创建新任务代次并计入每 5 分钟一次的成功提交限制。

### 归档、删除与文件

- 等待任务归档后立即取消；运行任务归档后尽力取消 CPA 请求并禁止晚到结果写入。岗位位置立即释放，但 CPA 执行额度只能在请求真正结束后释放。
- 恢复归档岗位不会自动恢复旧任务；需要解析时由用户手动重新提交。
- 正在用于进行中面试的岗位不能归档；面试结束或中断后可以归档，历史面试继续使用已保存的岗位画像快照。
- 公共岗位归档后从公共列表隐藏；恢复后若审核状态仍有效则重新公开。
- 未确认且从未用于面试的草稿或失败岗位可以永久删除；已确认、曾公开或曾用于面试的岗位只能归档，不能物理删除。
- 岗位上传的原始 PDF/TXT 不长期保存，只保存提取后的 JD 文本；删除和归档不再承担原始文件清理。
- 现有 uploads/positions 中无法关联的历史文件作为孤儿文件，另行提供人工核对和清理步骤，不由迁移脚本自动删除。

### 页面、故障恢复与历史数据

- 页面区分等待解析、解析中、待确认、失败和取消；排队时显示前面约有多少个用户轮次，以及本用户岗位顺序，不承诺固定不变的精确任务名次。
- 页面每 5～10 秒刷新服务端真实状态，不能在 60 秒后静默停止；关闭或刷新页面不影响后台任务。
- Redis 意外不可用时，新建、重新解析、归档和恢复失败快返；已有岗位查询仍可工作。本方案不提供 Redis 不可用时继续接收任务的降级路径。
- 当前单实例重启后，等待任务按持久化排队号恢复；运行中任务标记为解析中断，由用户手动重试。
- 旧 PENDING 岗位在 JD 非空且不超过 2000 字时恢复排队；旧 PARSING 岗位标记中断；PENDING_CONFIRM、CONFIRMED 和 PARSE_FAILED 保持原状态。
- 已完成的历史岗位即使 JD 超过 2000 字仍可查看，但再次解析必须满足新上限。无内容或超限的旧 PENDING 岗位标记失败。
- 已有岗位超过 5 个的老用户保留全部数据，但归档到限制以内前不能新建、重新解析或恢复归档岗位。
- 未来多实例共享同一 MySQL 任务记录和 Redis 队列，通过原子领取、任务条件更新、执行者标识、租约和跨实例 CPA 许可防止重复运行；当前阶段不提前引入 MQ。

## 关键问题、方案与决策过程

### 决策：使用 MySQL 持久化任务与 Redis 公平用户队列

- 当时的问题：内存队列重启即丢，Redis 单独保存完整任务无法承担最终业务状态，纯 MySQL 调度又会产生频繁扫描和难以理解的公平顺序。
- 不处理的后果：岗位可能永久停在解析中，服务崩溃后任务消失，用户顺序在重启后改变，或者调度器持续高频扫描数据库。
- 考虑过的方案：程序内存队列、Redis 单独队列、MySQL 持久化任务队列、MQ/Outbox、MySQL 任务加 Redis 等待用户索引。
- 最终选择：MySQL 保存真实任务、任务代次和固定排队号，Redis 保存可重建的等待用户队列；每个用户每轮只执行一个岗位后重新排到队尾。
- 选择原因：兼顾重启恢复、用户公平、快速调度和当前单实例复杂度，并允许未来多实例共享同一任务事实与 Redis 队列。
- 已查证事实或仍成立的前提：当前岗位只有简单解析状态且无任务代次；项目已使用 MySQL、Redis 和 Redisson；用户已确认 Redis 是岗位写入和调度的必备依赖。

### 决策：采用受控虚拟线程等待非流式 CPA 结果

- 当时的问题：同类调用 @Async 绕过 Spring 代理，LLM 实际在请求事务内同步执行；仅换后台普通线程又可能把请求阻塞变成线程池长期阻塞。
- 不处理的后果：创建页面长时间 loading、请求超时、数据库事务持续占用，并可能在 CPA 卡住时耗尽线程或连接。
- 考虑过的方案：继续同步、修复 @Async 并使用固定线程池、前后端流式、后台消费流式、持久队列加受控虚拟线程非流式调用。
- 最终选择：请求只持久化和排队；任务获后台 CPA 额度后使用独立虚拟线程执行非流式调用，15 分钟总超时后进入失败。
- 选择原因：岗位需要最终结构化 JSON而不需要逐字展示；虚拟线程降低等待线程成本，持久队列和 CPA 许可负责限制真实外部并发。
- 已查证事实或仍成立的前提：当前 Spring AI 调用本来使用 call().content() 获取完整响应；现有 timeout-seconds 未接入实际客户端；当前 ChatClient 每次调用重新创建，需要改为复用并完成真实长连接验证。

### 决策：用限制、全局等待上限和可见状态保护用户体验

- 当时的问题：仅设置后台并发数会让其他用户误以为失败，完全无限排队又可能产生等待数小时或数天但仍继续接收的假可用状态。
- 不处理的后果：单用户可以堆积任务，后来用户等待不可解释，坏文件可以持续消耗解析资源，全局队列可能无限增长。
- 考虑过的方案：全系统只允许少量任务且超出失败、每用户固定并发、无限公平队列、带用户限制和预计等待硬上限的公平队列。
- 最终选择：每用户最多 5 个未归档岗位、5 个等待任务、5 分钟成功提交一次、5 分钟 5 次文件上传；30 分钟提示、2 小时停止接收。
- 选择原因：用户之间仍能轮流，单用户不能占满系统，同时队列在容量异常时有明确停止接收条件，而不是无限积压。
- 已查证事实或仍成立的前提：后台并发数由 CPA 容量负责人提供；预计等待根据当前用户轮次、后台额度和近期解析耗时计算；正常目标为 10 分钟内开始解析。

### 决策：正式画像与重新解析候选版本分离

- 当时的问题：当前重新解析会把已确认岗位立即改为 PENDING，而新建面试只允许 CONFIRMED，导致岗位在长时间排队期间不可用；解析结果还会在用户确认前覆盖同一画像记录。
- 不处理的后果：用户重新解析一个可用岗位后可能 30 分钟以上无法开始面试，失败或旧任务晚到还可能破坏已确认结果。
- 考虑过的方案：重新解析立即使旧画像失效、解析期间继续使用旧画像但直接覆盖、正式画像与候选解析结果分离。
- 最终选择：正式画像继续可用，新解析结果单独保存为候选版本；只有用户确认后才原子替换正式画像并重新进入审核。
- 选择原因：保持面试可用性，允许失败和取消安全退出，并通过任务代次阻止旧结果覆盖新状态。
- 已查证事实或仍成立的前提：面试创建会保存岗位画像快照；当前代码注释声称重新解析期间旧画像可用，但实际 parseStatus 检查与该注释冲突。

### 决策：不长期保存岗位原始文件并限制 JD 输入

- 当时的问题：岗位文件保存后的路径没有持久化或使用，删除岗位也不会删除文件；10MB 文件可持续占满持久卷，超长 TXT 还可能形成巨量模型输入。
- 不处理的后果：部署磁盘持续增长，文件无法按岗位追踪清理，恶意或误上传内容可以消耗内存、CPU 和 CPA 输入容量。
- 考虑过的方案：继续保存并增加生命周期清理、迁移到对象存储、只在请求内提取文本并丢弃原始文件。
- 最终选择：原始文件不长期保存，只保留不超过 2000 字的提取文本；增加真实类型、大小、上传频率和提取并发保护。
- 选择原因：当前业务只使用 JD 文本，保留文件没有产品价值；不保存从根本上消除孤儿文件生命周期。
- 已查证事实或仍成立的前提：JdFileStorageService 返回的路径当前未被岗位实体或后续流程使用；JdTextExtractor 已能直接从 MultipartFile 提取文本。

### 决策：以归档保护历史，以受限永久删除处理无历史草稿

- 当时的问题：用户需要通过减少活跃岗位释放 5 个位置，但现有物理删除在面试结束解锁后仍可删除曾使用的岗位，可能破坏审核和历史引用。
- 不处理的后果：用户只能永久删除有价值的岗位才能继续创建，或者删除后历史面试和公共岗位关系出现缺失。
- 考虑过的方案：所有岗位只能物理删除、所有岗位永不删除只归档、草稿可删而有历史岗位只归档。
- 最终选择：归档作为默认释放位置方式；未确认且从未用于面试的草稿或失败岗位可永久删除，已确认、曾公开或曾用于面试的岗位只能归档。
- 选择原因：兼顾用户清理无价值草稿的需求与历史面试、审核和公共岗位数据的可追溯性。
- 已查证事实或仍成立的前提：面试记录保存 position_id 和岗位画像快照，当前删除只检查活动锁，结束后的历史岗位仍可能被物理删除。

## 未决事项与剩余风险

- CPA 实时池、后台池、多账户 Key 和具体并发上限由其他负责人提供；在拿到实际容量与限流语义前，不能确定后台许可数和预计等待计算的最终参数。
- CPA 非流式长回答是否会被 CPA、反向代理或中间网络提前断开尚未通过真实调用验证；如果长时间无响应数据会被关闭，需要重新评估仅后端消费流式响应。
- PDF 文本提取并发上限、后台并发数和监控告警阈值仍需结合部署 CPU、内存和 CPA 压测结果配置。
- Redis 被定义为必备依赖；Redis 故障时岗位写操作不可用是已接受的剩余可用性风险。
- MySQL 与 Redis 之间没有单一原子事务，必须实现并验证幂等补回；当前不引入 MQ/Outbox。
- 历史孤儿文件尚未清理，数据库迁移尚未编写或执行，业务代码、前端和配置均尚未实施。
- 当前单实例运行中任务在重启后需要用户手动重试；自动租约接管留到多实例阶段。
