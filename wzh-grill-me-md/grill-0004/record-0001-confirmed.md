- 核心决策：采用可插拔本地风险检测、类型化 LLM 入口、文档两阶段隔离、证据校验和服务端状态控制组成的分层防御
- 目标与边界：降低简历、JD、面试回答及模型派生内容中的 Prompt 注入成功率，并保证注入即使影响模型也不能自动成为正式事实、控制面试流程或扩大数据影响；本主题不实施代码，不处理题库、正式 RAG、长期记忆、日志优化及未来高危 Tool 执行策略

## 当前结论与确认内容

### 安全目标与基本边界

- 不宣称能够彻底阻止 Prompt 注入。目标是降低成功概率，并限制注入成功后的业务影响。
- 简历、JD、面试回答、用户反馈和历史模型结果始终是 `DATA_ONLY`。用户确认只确认内容用途或事实，不会赋予系统指令权限。
- Prompt 注入是攻击方式；目标或流程挟制、事实污染、重要性篡改、事实遗漏和数据泄露是需要分别防止的结果。
- 关键词、正则、专用分类器和外部 Prompt Shield 都只能产生风险信号，不能成为唯一安全边界。
- 当前没有向模型开放任意 HTTP、Shell、邮件等高危 Function Tool，因此现阶段重点是防止事实、评分、流程和后续上下文被污染。

### 外部内容进入模型前

```text
原始简历或 JD
→ 提取正文并生成规范化检测副本
→ 按原始位置分段并生成稳定 segmentId
→ 本地风险检测
→ 必要时由上传者一次性逐条确认
→ 才允许调用模型
```

- 文本段状态使用 `NORMAL`、`SUSPICIOUS`、`QUARANTINED`。`NORMAL` 只表示未发现已知风险，不代表内容可信或拥有指令权限。
- 多个 `SUSPICIOUS` 段一次性展示给上传者。普通段自动保留，用户勾选的可疑段保留，未勾选段排除；未完成确认时不调用模型。
- 个人简历和个人 JD 由本人确认。只有公共 JD 的异常内容才涉及管理员，不做全量管理员审核。
- `QUARANTINED` 不提供一键放行。确属正常正文时，应改成可见文字后重新上传。
- Unicode 检测覆盖零宽字符、双向控制符和异常同形字符，并保留规范化文本与原文位置映射。
- PDF 在提取阶段检查不可见渲染模式、透明度、极小字号、页面外坐标和异常重叠文字。
- Base64 和十六进制内容只在特征明确且长度受限时解码一次，禁止递归解码。
- MVP 不引入逐页 OCR 和视觉比对，也不宣称能够发现全部隐藏 PDF 注入。

### 可插拔风险检测能力

- 新增统一的可插拔检测接口，建议命名为 `PromptRiskDetector`。当前代码中尚不存在该接口，它属于待实施设计。
- 第一阶段提供本地确定性实现，负责指令式内容、Unicode 异常、PDF 隐藏内容和受限编码内容等风险信号。
- 统一 LLM 入口只依赖检测接口，不与具体检测产品绑定；以后可组合或替换为专用分类模型、Microsoft Prompt Shields 或其他检测器适配器。
- 检测器只返回风险类型、命中位置、置信信息和建议文本状态，无权决定 system prompt、业务动作、面试状态、模型厂商或权限。
- 第一阶段不调用第二个安全模型，也不接外部 Prompt Shield，避免增加费用、延迟和敏感数据接收方。
- 即使检测器漏判，类型化请求、证据校验、输出契约和服务端状态机仍必须阻止影响扩大。

### 统一 LLM 入口与模型路由

- 业务代码只能提交 `taskType`、类型化数据块和预期响应类型。
- system prompt 由服务端根据任务类型选择，业务代码不能自由提供，`DATA_ONLY` 内容不能进入 system message。
- 统一入口负责内容角色、长度、风险检测、输出契约、路由、重试和安全结果分类。
- 现有 Agent 全部迁移后，删除公开的 `chat(String, String)`，避免业务代码绕过防护。
- 简历、JD、回答按数据类型配置允许使用的模型厂商集合。
- 只有超时、限流和临时网络故障等基础设施失败，才能在批准范围内切换备用模型。
- Prompt 注入信号、证据失败、语义违规和结构错误不能触发跨厂商切换。

### JD 与简历的两阶段隔离

```text
确认后的 JD
→ 第一阶段只提取白名单事实和 evidenceRefs
→ Java 逐字段验证并检查明显事实遗漏
→ 第二阶段只读取验证后的事实和服务端知识
→ 生成岗位画像
```

- 第二阶段不能重新读取 JD 原文、完整证据文本或被隔离内容。
- 简历强化现有“原文事实提取 → 用户确认正式画像 → 辅助分析”两阶段，不机械增加第三次模型调用。
- 简历第二阶段只读取验证并确认后的结构化事实；简历原文、用户反馈和上一次模型分析都不能进入可信指令区域。
- 面试回答评估和出题不机械增加第二次调用，只发送当前问题、当前回答和最小必要上下文。

### 证据、规范化与遗漏检查

- 服务端预先生成稳定 `segmentId`。模型只返回候选值和 `evidenceRefs`，原始值由 Java 从当前文档对应段落读取，不能相信模型复制的 quote。
- 引用必须属于当前文档；非法或伪造引用不能进入第二阶段。
- 技能、年限、薪资、地点和枚举分别使用确定性规则；自由文本的大幅语义改写不能模糊自动放行。
- 现有简历技能别名规则应提取成共享组件，供简历和 JD 共用。因此 `Spring Boot` 与 `springboot` 可以通过规范化确认。
- `skill`、`importance`、`depth` 分别验证。技能名称匹配不能证明“必须”或 `L4` 等属性成立。
- 原文明示事实标记为 `EXPLICIT`；模型语义推导只能标记为 `INFERRED`，不能伪装成原文事实。
- 单个字段证据失败只丢弃该字段。至少保留一项验证过的岗位要求或职责，才能进入第二阶段。
- 模型调用前由 Java 建立已知技能、明确年限、学历等“明显事实清单”。遗漏项最多补为 `MENTIONED + UNKNOWN`，大量明显事实被遗漏时停止第二阶段。

### 面试状态、输出和报告

- 用户回答只用于评估，不能触发结束、跳题、换阶段或其他业务动作。
- 分数必须是 `0-100` 整数，枚举使用白名单，文本和集合有长度或数量上限。
- 模型不能返回或控制 `phase`、`topic`、`nextAction`、结束状态、题目计数、深度或厂商路由。
- 面试阶段、计数、深度和换题由服务端状态机决定。无效评估只产生“本轮评估不可用”的中性信号。
- 面试题只能解析为固定 DTO，并经过长度和安全校验；禁止使用正则片段或模型原文兜底展示。
- 回答框里的自然语言永远不执行控制动作。结束面试走现有 `/end` 接口，未来跳题也必须新增独立按钮和 API。
- 面试题生成失败可使用服务端固定、只读的安全模板。该模板不是动态题库，不拼接 JD、简历、回答或模型原文。
- 最终报告读取经过验证的逐轮结构化评估，不再重新发送完整问答记录。
- 综合分和维度分由服务端根据有效逐轮分数计算，不能按回答长度计算，也不能由报告模型决定。
- 报告模型只组织文字，并引用对应 `messageId` 和验证后的短证据；依据不足时显示不可用或部分完成，不生成通用赞扬或批评。

### 失败处理

- 普通 JSON 格式错误使用原类型化请求最多重试一次，不能把第一次非法响应作为新输入交给模型修复。
- 安全或语义违规不重试。单字段证据失败按字段丢弃；全部核心事实失效或大量遗漏时整次停止。
- 简历事实提取失败时任务失败并保留已有正式画像；JD 失败时保留旧成功结果。
- 简历辅助分析失败时继续使用上一次成功分析。
- 回答评估失败时不生成分数或优劣结论，也不累计优秀或失败次数。
- 面试题生成失败时使用固定安全模板；简历和 JD 不能使用通用内容兜底伪装成功。
- 最终报告依据不足时只展示可核验部分，评分和能力结论标记不可用。

### 已被替代、放弃或暂缓的内容

- 早期“JD 保持单次调用”的建议已被两阶段增强方案替代。
- 早期“可疑内容直接受限进入第一阶段”的建议已被“模型调用前由上传者批量逐条确认”替代。
- 早期“模型返回 quote 并逐字匹配”的设计已被 `segmentId` 和 Java 读取原文替代。
- `SAFE/SUSPICIOUS/BLOCKED` 已改为不会暗示可信性的 `NORMAL/SUSPICIOUS/QUARANTINED`。
- 放弃只靠关键词拦截、命中可疑词就拒绝整份文档、使用模型原文或正则抢救非法输出、增加第二个安全模型作为唯一判断者。
- 放弃使用当前动态题库作为安全兜底，改用独立的服务端固定安全模板。
- 题库、正式 RAG、长期记忆、共享内容审核和数据库风险元数据暂缓，不属于当前 Prompt 注入方案。
- 未来 Tool 权限、网络出口、SSRF 和高风险动作审批暂缓；当前不新增高危 Tool。
- 日志优化由用户后续单独处理。当前 DEBUG 原文日志是已知遗留风险，但不在本次实施范围。

## 关键问题、方案与决策过程

### 决策：将检测器设计为可插拔风险信号源而不是安全裁决者

- 当时的问题：关键词会误伤安全岗位 JD，也可以被改写或编码绕过；增加第二个模型或外部 Prompt Shield 同样存在误判、漏判、费用、延迟和隐私扩散。
- 不处理的后果：检测能力会与业务代码耦合，后续无法替换；或者系统会错误地把检测器输出当成权限判断，漏判一次就失去全部防护。
- 考虑过的方案：命中可疑词就全局阻断；完全不检测；接入第二个通用模型；使用本地确定性检测并预留可插拔接口。
- 最终选择：新增 `PromptRiskDetector` 接口，第一阶段采用本地确定性实现，未来允许组合专用分类器或外部服务，但检测结果只作为风险信号。
- 选择原因：能够控制第一阶段成本和隐私范围，也便于后续用攻击样本决定是否升级；安全边界仍由类型化请求、证据和服务端规则承担。
- 已查证事实或仍成立的前提：公开安全指南均不把单一检测器视为完整防线；当前项目没有专用检测接口，也没有需要模型直接执行的高危 Tool。

### 决策：可疑段在模型调用前由上传者确认

- 当时的问题：`SUSPICIOUS` 文本可能是真攻击，也可能是 AI 安全岗位中正常出现的“忽略之前规则”等描述，系统无法百分之百判断。
- 不处理的后果：自动删除会误伤正常内容；自动放行会让攻击原文直接进入模型；全量管理员审核会造成不可持续的工作量。
- 考虑过的方案：全局拒绝整份文档；所有可疑段受限进入模型后再确认结果；管理员逐份审核；上传者在模型调用前逐条确认。
- 最终选择：多个可疑段一次性展示给上传者逐条选择，确认后才进行模型调用；隔离段不得直接放行。
- 选择原因：只增加少量例外确认，不让管理员审核每份个人内容，同时在模型读取前消除用户明确排除的攻击段。
- 已查证事实或仍成立的前提：个人简历和个人 JD 的上传者能够判断哪些内容属于希望分析的正文；用户确认不会改变内容的 `DATA_ONLY` 权限。

### 决策：JD 新增两阶段，简历强化现有两阶段

- 当时的问题：JD 当前把不可信原文、服务端行业知识和最终画像推理放在同一次模型调用中，合法 JSON 也可能携带注入产生的业务污染。
- 不处理的后果：仅做输出结构校验仍可能接受“输出系统提示词”之类字段合法但语义被挟制的岗位画像。
- 考虑过的方案：JD 保持单次调用并加强 Prompt；所有调用都机械拆成两次；只对可先压缩成结构化事实的 JD 和简历使用两阶段隔离。
- 最终选择：JD 使用事实提取、Java 验证和岗位画像两阶段；简历强化已有事实提取、用户确认和辅助分析两阶段；回答评估和出题不机械拆分。
- 选择原因：第二阶段不接触原始攻击文本，同时避免给必须理解完整回答语义的交互场景增加无意义调用。
- 已查证事实或仍成立的前提：现有简历流程已经接近两阶段；JD 当前仍是一次模型调用混合原文提取与最终推理。

### 决策：使用服务端证据编号、逐字段校验和遗漏检查

- 当时的问题：模型可以改写 quote、伪造合法 JSON、篡改技能重要性，或只返回部分真实事实来隐藏其他岗位要求。
- 不处理的后果：两阶段只会把污染从原文转成 JSON，未经证实的内容仍然进入第二阶段。
- 考虑过的方案：只校验 DTO；要求模型复制原文 quote；完全使用本地规则提取；服务端分段编号并结合确定性解析和明显事实清单。
- 最终选择：模型只提供候选值和 `evidenceRefs`，Java 从当前文档段落读取原始值，按字段规范化验证，并在模型前后对比明显事实清单。
- 选择原因：不依赖模型精确复制文本，能够接受 `Spring Boot` 与 `springboot` 等确定性等价，同时拒绝无法证明的自由文本改写、重要性篡改和大规模遗漏。
- 已查证事实或仍成立的前提：项目已有简历技能别名和 `normalizeSkillName` 能力，但当前是简历模块私有实现，需要提取成共享组件。

### 决策：模型评估数据不能控制服务端流程

- 当时的问题：用户可在回答中要求高分、结束或换阶段，当前模型评估字段和兜底结果会间接影响连续优秀、失败次数及后续流程。
- 不处理的后果：直接 Prompt 注入可能升级为目标或流程挟制；非法题目还可能通过原文兜底直接展示给用户。
- 考虑过的方案：继续让模型返回流程建议；只忽略部分动作字段；将模型限制为经过严格校验的评分和评价数据，并由服务端状态机独立决策。
- 最终选择：模型不能返回流程控制字段，回答自然语言不能执行动作，题目和评估都使用固定 DTO；无效评估产生中性不可用信号，题目失败使用固定安全模板。
- 选择原因：把业务动作与不可信自然语言分开，即使模型受到影响也不能改变阶段、计数、结束状态或直接展示非法原文。
- 已查证事实或仍成立的前提：现有系统已有独立的回答接口和 `/end` 接口；未来跳题可以沿用独立按钮和 API 的模式。

### 决策：按失败类型控制重试、路由和最终报告

- 当时的问题：当前备用模型可能在任意异常后接收同一份敏感数据；格式、安全和证据失败混在一起处理；报告重新读取完整问答并按回答长度产生分数。
- 不处理的后果：敏感数据可能扩散到未批准厂商，攻击内容可通过重试或报告再次传播，长篇攻击文本还可能获得更高分。
- 考虑过的方案：所有失败自动重试和切换模型；任何失败直接中断；按基础设施、格式、安全、证据和业务场景分类处理。
- 最终选择：只有普通格式错误在同一批准路由内重试一次，只有临时基础设施故障可切换批准的备用模型；报告只使用验证后的逐轮评估，服务端计算分数。
- 选择原因：保留对偶发模型格式问题的容错，同时不把安全违规当成可以反复修复的普通异常，也不让报告重新暴露完整攻击上下文。
- 已查证事实或仍成立的前提：当前模型服务会在较宽泛的异常范围内调用备用模型；当前报告存在完整问答重发和回答长度计分逻辑。

## 未决事项与剩余风险

- 当前方案尚未实施。现有字符串版 LLM 入口、正则或原文兜底、宽泛备用模型切换和报告长度计分风险仍然存在。
- 本地检测器会漏掉未知表达、跨段复杂语义和新型编码；用户也可能错误确认恶意段落。
- 证据引用只能证明“候选字段来自哪段”，不能证明原文陈述真实，也不能独立证明复杂语义推断正确。
- 本地明显事实扫描只能覆盖已知技能、明确年限、学历等确定性内容，不能保证复杂职责完全不遗漏。
- PDF 高置信度检测无法覆盖复杂背景、图片文字和全部视觉隐藏方式。
- 日志优化、题库和共享持久化、RAG、长期记忆、数据库安全元数据、未来 Tool 权限及网络出口均需在独立主题中处理。
