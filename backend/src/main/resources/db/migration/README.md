# MySQL 数据库迁移说明

本目录中的版本化 SQL 是 Interview Coach 的 MySQL 表结构唯一事实来源。项目不维护另一份合并版“全量初始化 SQL”；一个数据库的完整结构由 V1 开始，按版本顺序逐步升级得到。

当前数据库结构基线为 **V4**，适用于 MySQL 8。

## 各版本负责什么

| 版本 | 脚本 | 作用 |
| --- | --- | --- |
| V1 | [`V1__init_schema.sql`](./V1__init_schema.sql) | 创建用户、简历、岗位、面试、题库、成长计划和审计日志等基础表、唯一约束与索引。 |
| V2 | [`V2__resume_profile_draft_analysis.sql`](./V2__resume_profile_draft_analysis.sql) | 增加简历解析生命周期字段、简历画像草稿与分析表，以及面试使用的简历分析快照。 |
| V3 | [`V3__resume_ai_task_control.sql`](./V3__resume_ai_task_control.sql) | 增加简历解析配额字段，以及简历 AI 分析任务的版本、模式、调用状态、可用状态和配额控制字段。 |
| V4 | [`V4__position_analysis_lifecycle.sql`](./V4__position_analysis_lifecycle.sql) | 增加岗位归档与解析任务生命周期、用户提交时间、面试岗位快照及相关索引。 |

## 应该执行哪些脚本

先根据数据库变更记录和实际表结构确认当前版本，再按下表执行。脚本不是幂等脚本，已经执行过的版本不能再次执行。

| 数据库当前版本 | 需要按顺序执行 |
| --- | --- |
| 全新空库 | V1 → V2 → V3 → V4 |
| V1 | V2 → V3 → V4 |
| V2 | V3 → V4 |
| V3 | V4 |
| V4 | 无需执行现有脚本 |

后续表结构发生变化时，应新增更高版本的 `V<版本>__<说明>.sql`，不能回头修改已经在任一环境执行过的脚本。

## 执行前后要注意什么

1. 先备份需要保留的数据，并确认当前没有仍在写入数据库的任务。
2. 这些脚本不会创建或切换数据库。执行前必须在 MySQL 客户端确认服务器、端口和目标数据库都正确。
3. 每次只执行一个版本，确认成功并记录已应用版本后，再执行下一个版本；遇到错误应立即停止，不要跳过失败语句继续升级。
4. V4 不会回填旧岗位、旧面试或旧任务数据。开发测试库升级前应清理无需保留的旧数据或重建数据库；如果必须保留既有数据，需要先单独制定与验证回填方案。
5. 全部脚本执行完成后再启动应用。默认配置使用 `spring.jpa.hibernate.ddl-auto=validate`，Hibernate 只校验实体映射与表结构，不会替代人工迁移。

## 账号与演示数据

- 迁移脚本只维护数据库结构，不创建普通用户或管理员。
- 首次管理员通过 `ADMIN_INIT_ENABLED` 和 `ADMIN_USERNAME`、`ADMIN_PASSWORD`、`ADMIN_NICKNAME` 创建，具体配置和安全要求见仓库根目录 README 的“首次创建管理员”部分。
- [`../../data.sql`](../../data.sql) 是 H2 本地开发使用的演示数据，不属于 MySQL 迁移，不要在 MySQL 中执行。

## 为什么不提供合并版全量 SQL

如果再维护一份 `init-all.sql`，同一套表结构就会有两个需要同步的来源，后续很容易出现字段、索引或约束遗漏。按 V1 到当前版本顺序执行，既能初始化空库，也能清楚记录已有数据库从哪个版本升级到哪个版本。
