## 当前有效需求

- 最终目标：把岗位 JD 的上传、排队、后台解析、候选确认、归档和删除改造成请求快速返回、任务公平等待、状态可信、失败可重试且不会泄漏文件的完整流程。
- 必须实现：
  - 创建岗位时只完成输入校验、文件文本提取、岗位与当前解析任务落库；不得在请求事务中等待 LLM。
  - MySQL 保存当前解析任务的真实状态，Redis 只保存可重建的公平排队顺序；不使用 MQ 和 Outbox。
  - 用户之间按轮次公平执行，同一用户的多个岗位按提交顺序执行，且同一用户最多同时运行一个岗位解析任务。
  - 每个普通用户最多保留 5 个未归档个人岗位、最多有 5 个等待任务；新建和重新解析共用“5 分钟最多成功发起一次”的限制，输入或上传校验失败不计次数。
  - 全部公共岗位任务作为一个独立排队参与者，每轮最多运行一个；公共等待任务上限可配置，初始按 20 个规划。
  - 全局岗位解析并发数必须可配置；只有取得执行名额后才创建 Java 21 虚拟线程，容量不足时任务继续排队而不是失败。
  - 岗位任务只使用 `WAITING`、`RUNNING`、`SUCCEEDED`、`FAILED` 四种状态，并用独立失败原因说明超时、中断、模型异常或结果无效。
  - 每个岗位只保留当前一次解析任务，不保留任务历史。重新解析删除旧候选和旧终态任务，创建新任务；确认候选后删除当前任务，只保留正式画像。
  - 后台解析成功只产生候选画像，必须由个人岗位所有者或公共岗位管理员确认后才能成为正式画像。
  - 重新解析期间，已有正式画像继续可用于新面试；新任务失败不能删除或降级旧正式画像。
  - 页面展示等待准备、前方大致等待量、解析中、待确认和失败，并轮询到当前任务结束；失败后提供重新解析入口，不再固定 60 秒后停止更新。普通用户端使用面向结果的中性文案，不说明“公平排队”等内部调度机制；管理端可继续展示必要的队列信息。
  - 岗位解析不向页面逐字流式输出；后台使用虚拟线程等待 CPA 返回，并遵守 CPA 层提供的最终调用上限。
  - JD 规范化后最多 2000 个 Unicode 完整字符，粘贴文本和上传文件都由前后端校验；该限制不作用于模型输出。
  - 上传仅支持 PDF/TXT，必须限制实际文件大小、真实类型、PDF 页数和提取资源；原文件只作临时提取，任何成功或失败路径都应关闭资源并清理，不再写入岗位持久卷。
  - LLM 调用、空结果或 JSON/Schema 校验失败必须把当前任务标记为失败，不能静默生成兜底画像并当作成功。
  - 删除岗位 JD 的跨用户 MD5 解析缓存；每次重新解析都必须真正生成新的候选结果。
  - 个人岗位只有本人可以创建、解析、确认、归档和永久删除，其他普通用户不能查看或操作。
  - 公共岗位只有管理员可以创建、解析、确认、归档和永久删除；普通用户只能查看已确认且未归档的公共岗位并用于面试。
  - 管理员确认公共岗位后立即公开，归档后立即下架；个人岗位不能直接转换为公共岗位。
  - 归档立即释放个人岗位数量名额并禁止新建面试；本阶段不提供恢复使用功能。
  - 归档等待中的岗位时直接删除等待任务；归档正在解析的岗位时保留运行记录到 CPA 调用真正结束，丢弃结果后删除任务并释放执行名额。
  - 永久删除只允许已归档、没有仍在运行的岗位任务且没有进行中面试的岗位。
  - 创建面试时保存岗位名称、公司、类别和正式画像的完整快照；面试过程、详情和报告不得再依赖原岗位记录。
- 必须保留：
  - 当前模块化单体和 `position`、`interview`、`admin` 的业务边界，不向 `gateway/` 迁移能力。
  - `/api/v1` 接口前缀、认证主体来源、统一响应和业务异常体系。
  - 已创建面试始终使用创建时保存的简历与岗位快照，不因后续重新解析、归档或删除改变。
  - 模型调用在数据库事务外执行；任务领取和结果写回使用短事务与源状态条件保护。
  - 当前工作树中用户及其他任务已经存在的修改，尤其是三个 YAML、部署文件、`goal-0001` 和未跟踪设计图，不覆盖、不回退、不整理。
- 明确排除：
  - 不处理任何旧岗位、旧公共岗位、旧待确认画像或旧任务的数据迁移、回填与兼容；当前开发数据可以放弃。
  - 不保存岗位解析任务历史，不增加 `SUPERSEDED`、`CANCELLING`、独立发布或审核状态。
  - 不实现归档岗位恢复使用。
  - 不使用 MQ、Outbox 或持续扫描数据库作为调度热路径。
  - 不实现多实例 Worker 租约、分布式调度主节点或跨实例总并发；未来扩容时另做 P2。
  - 不处理 CPA 多账户、Key 分配、供应商路由、实时面试容量预留的内部实现或底层 HTTP 取消；岗位模块只使用分配给它的 CPA 容量和外部调用契约。
  - 不新增、修改或运行单元测试，不代用户执行数据库脚本，不执行 Git 写操作。
- 验收偏好：本轮后续验收由 AI 在当前规则允许范围内主导，负责只读/无写接口、页面状态、轮询、日志和运行证据核对；真实或持久数据库的写入动作（包括通过页面/API 间接写入）仍由用户执行，最终页面观感仍由用户判断。涉及真实 Redis、真实 CPA、应用重启或前后端联调的具体运行操作，仍按项目规则说明操作与影响后执行。

## 约束与边界

- 项目约束：
  - 后端为 Java 21、Spring Boot 3.3.2、Spring Data JPA、Spring Data Redis、Redisson 和 Spring AI；生产依赖 MySQL 与 Redis。
  - 数据库结构只通过 `backend/src/main/resources/db/migration/` 下的新版本 SQL 增量管理；V1、V2、V3 不得修改。
  - `spring.jpa.hibernate.ddl-auto=validate`，应用代码和目标数据库结构必须一致。
  - 岗位 JD、画像与面试快照属于敏感业务数据，日志、错误和 Redis Value 不保存或输出正文。
  - 后端修改后按项目规则不编写或运行单元测试；前端修改后需要构建，视觉验收由用户完成。
- 环境约束：
  - 未来 3～6 个月按单实例后端实施，接受应用重启后把原运行任务标记失败并由用户手动重试。
  - Redis 按必需依赖规划；Redis 队列内容可以从 MySQL 的 `WAITING` 任务重建。
  - CPA 调用可能超过一分钟，但应由外部 CPA/LLM 层提供明确最终上限；岗位模块不能提前释放仍在执行的容量。
- 用户明确限制：
  - 旧开发数据无需保留，迁移脚本不写回填或兼容分支。
  - 数据库脚本只提供给用户手动执行，并说明执行顺序、影响、备份/重建与核对方式。
  - 当前阶段优先采用简单、可理解的实现，不为任务历史、旧数据或尚未发生的多实例部署增加状态和组件。

## 重要变化

- “普通用户端强调公平排队” -> “普通用户端只表达岗位画像正在准备，可按需显示前方大致任务量”：保留有用进度，隐藏不影响用户决策的内部调度机制。
- “页面和业务流程全部由用户自行验收” -> “用户只执行必要的持久化写入并确认最终观感，AI 接手其余可执行验证和证据整理”：减少用户逐项排查负担，同时保留数据库操作与主观验收边界。
- “调用同类 `@Async` 方法” -> “事务提交后由独立调度组件领取任务，取得执行名额后才创建虚拟线程”：消除请求同步等待和无界后台占用。
- “整个系统同时两个任务会使其他用户失败” -> “容量不足只排队，用户之间轮流执行”：并发限制只保护 CPA 和应用资源，不作为拒绝普通用户的理由。
- “程序内存队列或直接 Redis 队列” -> “MySQL 保存任务事实，Redis 保存可重建的公平顺序”：兼顾重启恢复与调度效率。
- “保留每次任务并增加替代、取消中状态” -> “每个岗位只保留当前任务，历史任务和多余状态直接删除”：降低当前阶段复杂度。
- “普通用户岗位经管理员审核后公开” -> “个人岗位永不转公共；公共岗位由管理员独立创建、确认即公开”：明确资源归属和权限。
- “永久保存上传文件” -> “只保留提取后的 JD 文本，上传原文件临时使用后清理”：消除未使用文件长期占盘。
- “只保存岗位画像快照” -> “面试同时保存岗位名称、公司、类别和正式画像完整快照”：岗位删除后历史面试仍完整。
