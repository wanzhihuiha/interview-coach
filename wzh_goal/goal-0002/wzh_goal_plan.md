## 方案目标与边界

- 方案目标：在现有模块化单体中建立“输入安全提取 -> MySQL 当前任务 -> Redis 公平排队 -> 有容量才启动虚拟线程 -> 候选确认 -> 归档/删除”的岗位生命周期，并让面试完全依赖创建时快照。
- 当前范围：岗位域的数据结构、创建/上传、任务状态、Redis 队列、单实例调度与恢复、候选/正式画像、个人与公共权限、归档/永久删除、面试岗位快照、Web 岗位页、面试配置页、管理端公共岗位页、配置、V4 SQL 和现有设计文档同步。
- 明确保留：模块化单体、`/api/v1`、统一认证与响应、正式岗位画像表、面试简历快照、当前 LLM 统一入口、现有 Redis 客户端和 Java 21。
- 明确不做：旧数据回填、任务历史、MQ/Outbox、归档恢复、多实例调度、CPA 多账户/Key/路由与底层取消、网关拆分、单元测试及自动执行数据库。
- 关键约束：MySQL 是任务事实来源；Redis 只保存投影；远程模型调用不进入事务；容量未取得不创建 Worker；任务记录必须保留到远程调用真实结束；个人和公共岗位的写权限严格分离。

## 当前方案

### 1. 数据与状态模型

- 新增 `position_analysis_task`，每个岗位最多一行当前任务，数据库唯一约束为 `position_id`。任务字段至少包含：自增 `id`、`position_id`、`request_user_id`、`queue_owner`、`status`、候选画像 JSON、失败代码与脱敏后的失败说明、开始/结束时间和创建/更新时间。
- 任务 `id` 同时作为创建后不再改变的固定排队号，只负责同一参与者内部 FIFO 和故障重建。`queue_owner` 对个人岗位使用 `USER:<userId>`，全部公共岗位使用同一个 `PUBLIC`；Redis 中的运行时轮转顺序负责“用户轮流、公共任务每轮一个”。
- 任务状态只保留 `WAITING`、`RUNNING`、`SUCCEEDED`、`FAILED`。超时、应用重启、线程启动失败、模型失败和结果无效只写入失败原因，不扩展状态枚举。
- `position_profile` 只保存已经确认的正式画像。`SUCCEEDED` 任务行中的结果是候选画像；确认时必须携带当前 `taskId`，在同一短事务中校验归属、岗位未归档、任务仍为 `SUCCEEDED`，再更新正式画像并删除任务。
- 重新解析只允许当前任务不在 `WAITING/RUNNING` 时发起；事务内删除旧 `SUCCEEDED/FAILED` 任务及其候选，保留正式画像，再创建新的 `WAITING` 任务。
- `position` 增加 `archived_at`；`sys_user` 增加个人岗位最近一次成功发起时间；`interview` 增加岗位名称、公司和类别快照字段，现有 `position_profile` 字段继续保存正式画像快照。
- V1 中的 `parse_status`、审核字段和相关索引本轮停止作为业务事实，但先保留数据库列，避免不必要的破坏式 DDL并保留代码回退能力；新接口不再依赖或暴露审核语义。

### 2. 创建、限额与事务

- 粘贴文本或文件提取先完成格式、大小和 2000 字校验；只有输入有效才进入创建事务，因此输入失败不消耗 5 分钟限制。
- 个人新建在数据库短事务中锁定当前 `sys_user` 行，再检查：未归档个人岗位少于 5 个、个人 `WAITING` 任务少于 5 个、距最近成功发起已满 5 分钟。
- 个人重新解析同样锁定当前 `sys_user` 行，并校验目标岗位属于本人、未归档、没有 `WAITING/RUNNING` 当前任务、个人 `WAITING` 任务少于 5 个且已过 5 分钟；重新解析不新增岗位，因此即使本人已有 5 个未归档岗位也不能被岗位数量上限误拦。
- 新建事务完成岗位、当前任务和最近成功发起时间写入；重新解析事务完成旧终态任务删除、新 `WAITING` 任务和最近成功发起时间写入。任一步失败全部回滚；事务成功提交才算一次成功发起。
- 个人限制由用户行锁串行化，一岗位一任务由数据库唯一约束兜底。公共岗位由管理员入口创建或重试，使用项目已有 Redisson 能力获取固定 `PUBLIC` 提交锁，在一个短事务内检查可配置等待上限并写入任务；Redis 锁不可用或未取得时失败关闭，不绕过上限。公共任务不占普通用户的岗位数与 5 分钟限制。
- 事务提交后发布轻量入队事件，由独立 Bean 和具名有界执行器把 `taskId` 幂等写入 Redis；HTTP 请求不等待 Redis 重试，更不能在该监听器中调用 LLM。Redis 入队失败不能回滚已提交任务；有界重试耗尽后保留 MySQL `WAITING` 并告警，应用重启时按 MySQL 重建。调度热路径不持续扫描 MySQL。

### 3. Redis 公平队列与单实例调度

- Redis 保存三类可删除投影：每个 `queue_owner` 的任务有序集合、全局可运行参与者轮转队列/成员标记、当前忙碌参与者标记。Lua 或等价原子操作保证同一参与者不会重复进入轮转，也不会在已有任务运行时因新任务入队而再次变成可运行。
- 新参与者加入当前轮转尾部。单线程调度器取得全局容量后，原子地把一个参与者从可运行队列移到忙碌集合并取出其队首任务，再用 MySQL `WAITING -> RUNNING` 条件更新确认领取；领取失败必须清除忙碌标记、按剩余任务恢复参与者并归还容量。当前任务真实结束且仍有 `WAITING` 时，才清除忙碌标记并把参与者放回轮转尾部。
- 启动重建先停止调度，清空本 Goal 专属 Redis 投影，把遗留 `RUNNING` 收口后，再按任务 `id` 升序恢复各参与者队列，并按各参与者最早 `WAITING` 任务号重新建立轮转，最后启动调度器。同一参与者内部顺序不会改变；不承诺保留重启前瞬时的参与者轮转位置，因此页面 `queueAhead` 可以在重启后变化，但恢复后仍继续按轮次公平执行。
- 页面显示的 `queueAhead` 是当前快照，不承诺完成时间；新参与者加入、任务归档或 Worker 完成后允许变化。
- 当前单实例使用一个受控调度组件和本地可配置容量许可。只有 Redis 预留和 MySQL 条件领取都成功后才调用 Spring 管理的专用虚拟线程 `ExecutorService`；提交线程失败时把已领取任务收口为 `FAILED`，清理参与者并归还许可。调度器不使用公共线程池，不依赖同类 `@Async` 调用，也不在等待容量时创建虚拟线程。

### 4. Worker、失败与恢复

- Worker 只接收 `taskId`，在事务外读取不可变任务输入并调用 `JdAnalysisAgent`/`LlmService`；数据库连接和事务不能跨越 CPA 等待。
- `JdAnalysisAgent` 对空输入、空画像、非法 JSON、Schema 不满足或 LLM 异常直接抛出可归类失败，不再返回兜底画像；日志只记录任务 ID、阶段、异常类型和耗时，不记录 JD、模型正文或完整候选 JSON。
- 成功写回使用短事务并要求：任务仍是当前任务、状态仍为 `RUNNING`、岗位未归档且归属/公共类型匹配。条件不满足时丢弃迟到结果，不覆盖正式画像。
- Worker 只有在底层 CPA 调用真正返回或抛错、数据库收口和临时资源清理完成后，才在 `finally` 中释放本地容量并唤醒下一轮；业务截止时间不能被当成“远程请求已经停止”。
- 应用启动恢复必须先于调度器开放领取：把未归档岗位的遗留 `RUNNING` 任务改为 `FAILED`，失败原因为应用重启中断且不自动重跑；归档岗位的遗留任务直接清理；再恢复有效 `WAITING`。关闭时先停止新领取，再按 Spring 生命周期关闭执行器；硬中断仍由下次启动收口。
- 岗位模块使用非流式模型结果。当前 `LlmService.chat(systemPrompt,userPrompt)` 没有逐调用 deadline 参数，且共享配置仍存在 60 秒超时；本 Goal 只要求岗位 Worker 不提前释放容量，并依赖 CPA/LLM 负责人提供可配置的岗位最终上限。多账户、路由和底层取消不在本 Goal 修改范围。

### 5. 文件和 JD 输入

- 前端粘贴文本使用 Unicode code point 计数并展示 2000 字上限；TXT 在上传前读取并预校验，PDF 使用成熟的浏览器 PDF 解析库做页数/提取文本的早期校验。前端结果仅用于提示，不能替代后端。
- 后端统一规范化 BOM、换行和首尾空白，再使用 `String.codePointCount` 做权威的 1～2000 字校验。
- 后端不再调用持久化的 `JdFileStorageService.store`。上传内容只写入服务端随机命名的非持久临时文件，不能使用客户端文件名控制路径。
- 后端再次校验实际字节数、内容特征与声明格式，PDF 使用 PDFBox 从临时文件打开并检查加密、页数和提取结果；TXT 使用严格 UTF-8 解码并拒绝明显二进制内容。
- 文件大小沿用 10 MiB 上限；PDF 最大页数、提取超时、提取并发和临时目录改成 `position.upload.*` 可配置项。提取执行资源有界，资源忙时快速失败。
- PDF 提取使用独立有界资源；提取 Worker 是临时文件和 PDF 资源的唯一清理责任人。请求等待超时可以返回失败，但不能假装底层提取已经停止或提前释放提取名额；Worker 真正结束后才在 `finally` 关闭资源、删除临时文件并释放名额。提交拒绝等尚未移交给 Worker 的路径由请求侧立即清理。启动时只按明确前缀和年龄清理能够确认属于岗位临时目录的孤儿文件。

### 6. 岗位权限、归档和永久删除

- 普通用户入口始终创建 `is_public=false` 的个人岗位；所有读取、确认、重新解析、归档和删除查询最终都携带 `userId` 和目标状态条件。
- 管理员公共岗位入口位于 `/api/v1/admin/positions` 并由 `hasRole('ADMIN')` 保护；服务层再次要求目标为公共岗位。任何管理员可以管理公共岗位，但不能借管理员公共入口改变个人岗位。
- 公共岗位存在正式画像且未归档时即公开。普通用户对公共岗位只有列表、详情和创建面试的读取权，不能确认、重新解析、归档或删除。
- 个人岗位永远不能修改为公共岗位；删除现有“用户岗位审核后公开”的业务流程和管理页面语义。
- 归档使用幂等短事务：立即写 `archived_at`、释放个人 5 个岗位名额并禁止新面试；`WAITING/SUCCEEDED/FAILED` 当前任务直接删除，`RUNNING` 任务保留到 Worker 真正结束并由 Worker 删除。
- 永久删除只允许已归档、当前没有 `RUNNING` 任务且不存在 `IN_PROGRESS` 面试。删除岗位、正式画像和残留终态任务；历史面试快照不删除。本阶段没有取消归档接口。

### 7. 面试完整快照

- 创建面试先在独立短事务中锁定并重新校验本人简历和目标岗位：岗位必须是本人的未归档个人岗位，或已确认且未归档的公共岗位；同时保存岗位名称、公司、类别和正式画像快照，创建面试并锁定简历，个人岗位再写面试锁，随后立即提交。公共岗位只在该准备事务内用行锁串行化归档竞态，不写全局面试锁。
- 准备事务提交后，`CoordinatorAgent` 才在事务外初始化上下文并调用 LLM 生成首题；首题与计数由第二个短事务写回。生成失败时使用短补偿事务把该面试标记为 `INTERRUPTED` 并释放简历/个人岗位锁；进程硬中断继续由现有启动清理收口，不能为了原子外观把远程调用放回长事务。
- `InterviewService` 的面试详情、报告生成、报告脱敏和后续回答都读取面试快照；`CoordinatorAgent` 不再通过 `positionId` 查询岗位类别。
- 个人岗位是否正在其他面试中继续沿用现有锁语义；公共岗位不写全局岗位锁，允许不同用户同时使用。永久删除统一通过 `InterviewRepository` 查询是否存在进行中面试。
- 岗位归档不打断已经开始的面试；永久删除后历史详情和报告仍能显示原岗位信息。

### 8. 前端状态与交互

- `Position` 前端类型拆分“正式画像是否可用”和“当前任务到哪一步”，不再把 `parseStatus=CONFIRMED` 同时表示两件事。
- 创建/上传响应返回后立即关闭弹窗并插入 `WAITING` 岗位；页面使用轻量状态接口轮询，按页面可见性和当前任务状态停止/恢复，不设置固定 60 秒总次数。
- 个人岗位页显示队列位置、解析失败原因和重试按钮；已有正式画像重新解析时仍显示可用于面试，同时单独显示新任务状态。
- 普通用户端将 `WAITING` 表述为“岗位画像准备中/画像更新准备中”，可以显示 `queueAhead` 的大致数量，但不宣传“公平排队”或解释内部调度机制；管理端仍可保留队列位置等运维信息。
- 增加未归档/已归档视图、归档确认和受约束的永久删除；归档列表只读查看，不提供恢复。
- 面试配置页以 `profileUsable=true && archived=false` 选择个人岗位，并合并已公开的公共岗位，不再按旧 `parseStatus` 过滤。
- 管理端现有“审核用户岗位”页面改为“公共岗位管理”：管理员独立创建/上传、查看状态、确认候选、失败重试、归档和永久删除；确认即公开，不再保留通过/拒绝按钮。

## 关键决策

| 决策点 | 结论 | 理由 | 影响 |
|---|---|---|---|
| 任务事实与排队 | MySQL 当前任务 + Redis 可重建公平投影 | 避免纯内存丢任务和把 Redis 当永久事实，同时不让调度持续查库 | 新增任务表、Redis 队列与启动恢复 |
| 并发执行 | 容量不足只等待；取得许可后才创建虚拟线程 | 保护 CPA/应用资源且不让后来的用户直接失败 | 新增单实例调度器和可配置许可 |
| 公平性 | 参与者轮转 + 参与者内 FIFO | 防止单个用户一次提交多个岗位长期占用容量 | 公共任务作为一个独立参与者 |
| 任务历史 | 只保留当前任务 | 当前开发阶段没有审计与恢复历史需求 | 不增加替代/取消中状态；重试替换旧任务 |
| 候选与正式画像 | 候选放当前任务，正式画像独立保留 | 新解析失败时旧正式画像仍可使用 | 确认接口必须携带当前 taskId |
| 个人与公共岗位 | 两类岗位从创建入口即独立 | 防止未经用户同意把个人 JD 公开 | 删除旧审核公开流程，新增管理员创建流程 |
| 公共发布 | 管理员确认即公开，归档即下架 | 满足当前简单流程，不增加发布状态 | 公开条件由正式画像和 archived_at 推导 |
| 文件保存 | 原文件仅临时提取，永不作为岗位持久数据 | 当前持久路径没有消费者且会泄漏磁盘 | 替换持久存储服务与清理流程 |
| 面试依赖 | 创建时保存完整岗位快照 | 允许岗位最终删除且不破坏历史面试 | Interview/Coordinator/报告读取改用快照 |
| 旧数据 | 全部放弃，不回填 | 当前仍在开发且没有需要保留的数据 | V4 只建立新结构；部署前由用户清理开发数据 |

## 重大未决问题

- 无。CPA/LLM 的账户、路由、实时容量预留和底层最终超时由其他负责人实现，是已明确排除的外部依赖，不改变本 Goal 的岗位任务、排队和写回结构。

## P2 判断

- 结论：需要
- 理由：当前按用户确认的单实例窗口实现；当后端扩展到多个实例时，本地许可和单实例调度唤醒不再能保证全局容量与每参与者单运行，需要独立演进，但现在提前实现会增加租约、主节点和故障恢复复杂度。

### P2 概要

- 目标：支持多实例 Worker、全局 CPA 容量、分布式领取/租约与恢复，并按届时实际 CPA 账户路由。
- 进入条件：确定部署两个以上后端实例，或 CPA 容量协调服务提供稳定契约。
- 预计范围：Redis/数据库条件领取、分布式 permit/lease、恢复 leader、实例心跳、迟到 Worker 防写回、队列校准和容量监控。
- 主要风险：重复领取、租约过期后旧 Worker 写回、全局容量超发、恢复任务并发和多账户路由不一致。

## 契约、迁移与切换

### API 目标契约

| 接口 | 目标语义 |
|---|---|
| `POST /api/v1/positions`、`POST /api/v1/positions/upload` | 只创建个人岗位和 `WAITING` 任务，返回 `positionId/taskId/latestTaskStatus`，不等待 LLM |
| `GET /api/v1/positions` | 只返回本人岗位，支持未归档/已归档筛选；列表同时返回 `profileUsable` 与当前任务摘要 |
| `GET /api/v1/positions/{id}/analysis-status` | 返回当前任务状态、`queueAhead`、失败原因、`profileUsable/canConfirm/canRetry`，供轻量轮询 |
| `GET /api/v1/positions/accessible` | 保留首页组合查询职责，只返回本人未归档且正式画像可用的个人岗位，以及已确认未归档的公共岗位 |
| `GET /api/v1/positions/{id}` | 本人可查看自己的未归档/已归档岗位；普通用户只能查看已确认未归档公共岗位，其他个人岗位按不存在处理 |
| `GET /api/v1/positions/{id}/profile` | 返回正式画像、当前候选、taskId 和权限能力；二者不得混为同一结果 |
| `PUT /api/v1/positions/{id}/confirm` | 请求携带 `taskId + profile`，只确认本人当前 `SUCCEEDED` 候选 |
| `PUT /api/v1/positions/{id}/reparse` | 受个人 5 分钟限制并替换旧终态任务/候选，保留正式画像 |
| `PUT /api/v1/positions/{id}/archive` | 幂等归档本人岗位，释放岗位名额并处理当前任务 |
| `DELETE /api/v1/positions/{id}` | 仅永久删除本人已归档、无运行任务且无进行中面试的岗位 |
| `GET /api/v1/positions/public` | 只返回未归档且已有正式画像的公共岗位，普通用户只读 |
| `/api/v1/admin/positions/**` | 管理员独立创建/上传公共岗位并完成状态查询、确认、重试、归档和删除 |
| 旧 `PUT /api/v1/positions/{id}/audit` | 删除调用方和业务语义，不再把用户岗位变为公共岗位 |

- 响应不再让 `parseStatus` 同时代表画像和任务；统一使用可空 `latestTaskStatus`、`profileUsable`、`canConfirm`、`canRetry`、`archived` 和任务失败摘要。
- 创建、确认、重试、归档、删除和权限拒绝使用可区分错误码；不存在与越权对普通用户不泄露其他人的资源信息。
- 当前开发阶段前后端同批切换，不维护旧 DTO 或旧审核接口的并存期。

### 数据与迁移

- 新增 V4，只做结构扩展和索引，不修改 V1～V3，不回填旧岗位/任务/面试。
- 用户执行前必须确认目标开发库、接受旧开发数据丢弃并自行备份或准备重建；Goal 实施只提供脚本、顺序和核对 SQL。
- 推荐切换顺序：停止旧应用 -> 用户清理无需保留的开发数据/备份 -> 用户执行 V4 -> 核对表、列、索引 -> 部署同步后的后端与前端 -> 启动时由 Hibernate `validate` 核对。
- 旧 `parse_status/audit_*` 列本轮不删除，因此代码回退到旧版本时结构仍兼容；新任务表和新增快照列不会被旧代码使用。
- Redis 岗位队列是投影，回退或修复时可以只删除明确的 `position:analysis:*` Key，再由新应用启动重建；不得扫描或删除其他业务 Key。

### 配置与运行

- 新增配置族：岗位并发、个人/公共等待上限、提交间隔、JD code point 上限、PDF 页数、提取等待上限、提取并发/队列、临时目录。岗位模块不配置一个无法终止底层 CPA 请求的“强制执行超时”；CPA 最终上限继续由外部调用层负责。
- `position.analysis.max-concurrency` 必须不超过 CPA 负责人分配给岗位后台任务的容量；本地开发可使用 2 作为显式默认，但该值不是业务固定上限。
- 岗位任务不复用简历 AI 的用户额度、许可或任务状态，不修改 `goal-0001` 的简历语义；只复用现有 Redis/Redisson 客户端和 Java 21 工程能力。
- 当前工作树中的 `application.yml`、`application-local.yml` 和 `application-test.yml` 已有用户修改，实施时必须逐项合并，不能覆盖真实凭据或其他任务配置。

## 风险与回退

| 风险 | 影响 | 预防或回退 |
|---|---|---|
| MySQL 已提交但 Redis 尚未入队时进程退出 | 任务暂时停在 `WAITING` | 任务事实保留在 MySQL；应用启动按 taskId 重建 Redis |
| Redis 运行中故障且应用不重启 | 新任务可能暂时无法调度 | 有界重试并记录告警；Redis 是必需依赖，恢复后人工重启可重建；不伪造任务失败 |
| CPA 调用超过业务期望且底层不响应取消 | 一个容量长期被占，用户任务继续等待 | 不提前释放许可；依赖 CPA/LLM 负责人提供最终上限；页面保持真实 `RUNNING` |
| PDF 在同一 JVM 中出现异常内存/CPU消耗 | 请求延迟或进程资源压力 | 文件大小、页数、提取并发、超时和临时文件控制；不宣称 JVM 内存绝对硬隔离 |
| 不保留任务历史 | 难以追溯多次解析详情 | 当前仅保留失败原因和日志标识；未来有明确审计需求再单独设计，不提前加状态 |
| API 同批重构 | 旧前端与新后端短期不兼容 | 开发阶段同步切换；回退时后端和前端一起回退，旧数据库列仍保留 |
| V4 与实体不一致 | `ddl-auto=validate` 阻止启动 | 先静态对账，再由用户执行并核对；代码回退不依赖删除新增结构 |
| 面试准备事务已提交但首题生成失败或进程中断 | 可能留下没有首题的 `IN_PROGRESS` 面试并占用简历/个人岗位锁 | 已知失败用短补偿事务标记 `INTERRUPTED` 并释放锁；硬中断复用启动清理；首题 LLM 不回到数据库事务 |
| 当前工作树和 Goal-0001 有并行修改 | 实施时可能覆盖用户或另一任务成果 | 每个工作包开始前重读 diff，限于目标文件合并，不回退或格式化无关内容 |
| 项目规则禁止单元测试 | 并发和恢复缺少自动化回归证据 | 明确保留风险，以静态审查、编译、构建和经授权人工场景验证，不把未运行测试写成通过 |
| 应用或 Redis 重建改变瞬时轮转位置 | 页面看到的前方任务数可能跳变 | 固定 taskId 保证参与者内 FIFO；重建后重新建立公平轮转，不承诺恢复崩溃前的精确 `queueAhead` |
