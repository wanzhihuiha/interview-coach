## 当前有效需求

- 最终目标：在未来 3～6 个月“用户使用自己的简历进行模拟面试”的范围内，完成简历事实画像、辅助分析重新生成、并发与每日额度控制的后端闭环。
- 必须实现：
  - 简历事实解析继续调用大模型，但正式事实画像只保存原简历中可核对的结构化事实；优势、待验证点和推断技能水平继续保存为独立辅助分析，不能反写成事实。
  - 手动辅助分析支持 `REGENERATE` 和 `REFINE`。前者只使用当前正式事实，后者使用当前正式事实、同一事实版本的上一次成功分析和本次用户意见。
  - `REFINE` 必须存在可解析的成功分析、其结果事实哈希严格匹配当前正式事实，且同一简历没有正在执行的 AI 任务；任一条件不满足时只允许 `REGENERATE`。用户并发与每日额度仍由提交接口最终校验。
  - 被接受的新分析任务开始后，旧分析立即停止参与之后创建的面试，但旧数据保留到新任务成功，供页面展示和 `REFINE` 参考；新任务失败不恢复旧分析。
  - 辅助分析的结果来源版本只描述当前保留的成功结果；从未产生成功结果时应为空，不能拿当前在途任务的事实版本冒充成功结果来源。
  - 用户意见只影响分析角度和重点，不能增加事实或直接指定技能等级；后端不保存、不回显、不记录意见正文。
  - 发送外部模型前尽力移除姓名、联系方式、证件、生日和详细地址；命中敏感内容后发送剩余脱敏内容，不因命中而整体拒绝。
  - 事实解析和辅助分析共享“每用户最多 5 个 AI 任务、同一份简历最多 1 个 AI 任务”的分布式并发限制；第 6 个用户任务或同简历第 2 个任务立即拒绝，不进入后台队列。
  - 使用 Redisson 可过期许可及续期机制；后台 Worker 使用 Java 21 虚拟线程，文件提取、脱敏、模型调用和结果写回保持在同一个任务线程中。
  - 手动事实重解析、计费后的 `REGENERATE`、`REFINE` 按 `Asia/Shanghai` 自然日共享每天最多 5 次成功、10 次尝试。每个任务只有真正准备进入模型调用时才计一次尝试；主模型、备用模型和内部自动重试合并为同一次用户尝试；进入调用后即使失败也占一次尝试，但失败不占成功次数。
  - 并行手动任务必须预留成功名额，保证“成功数 + 运行中预留数”不超过 5；失败或未开始模型调用时按已确认语义释放对应预留，Redis 状态转换必须原子化。
  - 正式事实画像确认与可选辅助分析彻底解耦：事实确认必须正常成功；确认提交后只有拿到 AI 并发许可才自动登记并执行免费 `INITIAL`，没有许可时不排队、不创建 AI 任务，也不能回滚或报失败覆盖已经确认的正式事实。
  - 每份新简历的首次事实解析和首次真正进入模型调用的辅助分析免费。辅助分析首次免费资格以持久化的“首次模型调用已开始”状态为准，而不是以任务是否创建、排队或失败为准。
  - 用户之后手动选择完全重新生成时，只要该简历的辅助分析从未真正进入过模型调用，后端仍按免费 `INITIAL` 执行且不占每日额度；首次模型调用一旦开始，无论最终成功或失败，首次免费资格均已使用，之后手动分析进入每日额度。序列化、脱敏或其他调用前失败不得消耗首次免费资格或尝试次数。
  - 重新解析后事实哈希未变化时，不重复已经真正进入过模型调用的辅助分析；若首次免费资格仍未使用且同简历没有执行中任务，本次确认后仍可按上述非阻塞规则尝试第一次 `INITIAL`。事实哈希变化时立即停用不匹配的旧结果；首次免费资格未使用时仍可尝试自动 `INITIAL`，资格已使用时由用户手动 `REGENERATE` 并进入每日额度。
  - 每用户最多保留 5 份当前未删除的简历；删除后可以继续上传。每用户每天最多新建 5 份简历，删除不返还当天新建次数。
  - 上传文件已经写入本地存储后，如果数据库创建简历或必要任务登记失败，后端必须尽力删除本次文件，不能把数据库回滚误认为文件也会自动回滚。
  - 重试 API 增加 `mode` 和可选 `feedback` 请求体；画像响应返回保留的旧分析、最新任务状态、是否可参与新面试以及是否允许 `REFINE`；并发、同简历任务、额度、数量和模式不可用必须可区分。
  - 保持事实解析缓存默认关闭；以后开启时继续按用户、Prompt、Schema 和文本哈希隔离，手动事实重解析必须强制绕过缓存。
  - 新增 V3 数据库迁移脚本，V2 不得修改；数据库脚本由用户手动执行。
- 必须保留：
  - 每份简历最多一条辅助分析记录，不增加用户可查看或恢复的历史版本。
  - 已创建面试始终读取创建时保存的事实画像和辅助分析快照，不在面试进行中切换。
  - 所有简历读取、状态变化、重试、删除和面试创建继续按认证用户校验资源归属。
  - 模型调用在数据库事务外执行；数据库状态推进使用短事务和代次/哈希守卫。
  - 当前工作树中用户和其他窗口已经存在的修改，特别是 `frontend/web/` 修改，不覆盖、不回退、不整理。
- 明确排除：
  - 不修改前端；前端弹窗、页面内存暂存意见和接口适配由另一个任务处理。
  - 不提供历史分析版本列表、恢复、回滚或长期审计正文。
  - 不持久化用户调整意见，也不在应用重启后恢复意见；失败或重启后由用户重新输入。
  - 不增加所有用户共享的系统总并发上限，不替模型供应商设计全局限流。
  - 除“正式事实已提交后，可选 `INITIAL` 无法准入时只跳过分析”这一已确认边界外，不设计 Redis 不可用时的业务降级；上传新建、手动任务准入、额度和每日新建限制仍把 Redis 视为必需依赖并失败关闭。
  - 不新增持久化任务队列，不在 `gateway/` 拆分服务，不进行模块化单体之外的架构迁移。
  - 不保存已删除简历正文或文本哈希做永久去重；接受删除重传在每天 5 份范围内再次获得首次免费流程。
- 验收偏好：本轮审查整改先完成后端实现、静态复审和离线 `mvn -o -DskipTests compile`；按当前项目规则不新增、修改或运行单元测试。V3 已由用户手工执行并核对字段；MySQL/Hibernate、真实 Redis、应用启动和全量测试继续作为未执行验证明确记录。

  - 公共 API 前缀保持 `/api/v1`；新增或实质修改请求使用 DTO，不直接暴露实体。

  - 简历、画像、反馈和日志均按敏感数据处理，不在测试、日志或 Goal 文档中保存真实正文或可识别信息。

- 用户明确限制：

## 重要变化

- “重试时清空旧分析” -> “旧分析保留但立即停用，成功覆盖、失败不恢复”：既支持 `REFINE` 参考，也避免失败后旧结论重新参与面试。
- “完全重新生成” -> “`REGENERATE` 与 `REFINE` 两种显式模式”：用户可选择完全重做或按本次意见调整。
- “本地固定线程池控制并发” -> “Redisson 分布式许可 + Java 21 虚拟线程”：并发限制按用户和简历生效，第 6 个任务立即拒绝。
- “只限制手动成功次数” -> “5 次成功、10 次尝试并原子预留运行中成功名额”：失败不占成功次数，但会占真正发生过的尝试。
- “没有简历数量约束” -> “最多保留 5 份且每天最多新建 5 份”：删除释放保留数量，但不返还当日新建次数。
- “确认正式事实后必定登记辅助分析任务” -> “事实确认先独立成功，许可可得时才自动登记免费 `INITIAL`”：没有许可不排队、不创建任务，也不影响正式事实用于面试。
- “首次任务创建即视为免费资格已使用” -> “首次真正进入模型调用才使用免费资格”：调用前失败保留资格，调用开始后的失败不返还资格。
- “上传文件依赖数据库事务回滚” -> “文件写入后显式补偿”：数据库创建或必要任务登记失败时尽力删除本次文件。
